# AGENTS.md

AmWF is a single-module Android app (`:app`) for rooted Qualcomm Snapdragon devices. It controls WiFi monitor mode through Qualcomm's `con_mode` and includes a WPS Pixie Dust audit flow. Kotlin + XML/ViewBinding + AppCompat/Material 3; no Compose and no DI framework (dependencies are constructed manually).

Deep-dive prose lives in `docs/` (`ARCHITECTURE`, `BUILDING`, `COMPATIBILITY`, `TROUBLESHOOTING`, `USER_GUIDE`) and in `CONTRIBUTING.md`, which mirrors the invariants below for external contributors (keep them in sync when you change one). Where prose conflicts with Gradle files, scripts or code, trust the executable source.

## CodeGraph

- The index is built and current (`codegraph status` → "Index is up to date"; ~67 files / 1.5k nodes); MCP `codegraph_explore` works. Prefer it over grep+read loops for symbols, call paths and blast radius.
- `.codegraph/` holds machine-local artifacts (DB/WAL, `daemon.pid`, sockets, logs), all ignored by its `.gitignore`: never commit them.
- After code changes, refresh with `codegraph sync` (or `codegraph index` for a full rebuild) and confirm with `codegraph status`. On a fresh machine the index is absent — indexing is the user's decision, so ask them to run `codegraph init` and fall back to built-in Grep/Read/Glob meanwhile.

## Build and verification

- Single module: all tasks are prefixed with `:app` (the root project applies no Android plugins, so bare tasks like `./gradlew assembleDebug` do not exist).
- Debug APK: `./gradlew :app:assembleDebug`
- JVM unit tests: `./gradlew :app:testDebugUnitTest`
- One test class: `./gradlew :app:testDebugUnitTest --tests "com.hitomatito.amwf.wifi.pixiedust.M3ParserTest"`
- Lint: `./gradlew :app:lintDebug`
- Full local check: `./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug`
- Instrumented tests: `./gradlew :app:connectedDebugAndroidTest` (`app/src/androidTest` has no test files; real monitor-mode and Pixie Dust behavior requires a rooted ARM device, and the native assets are ARM-only, so x86/x86_64 emulators cannot run them).
- CI runs on GitHub Actions (`.github/workflows/ci.yml`): the full check (`:app:testDebugUnitTest :app:lintDebug :app:assembleDebug`) on pushes to main, PRs and manual dispatch, with the debug APK uploaded as a run artifact. The 16 KB ELF alignment step is **blocking**: the arm64 assets are rebuilt aligned (all `LOAD` segments at `0x4000`) and any 4 KB regression cuts the run — Play has rejected targetSdk 35+ updates without it since 2025-11-01. There are still no pre-commit hooks or task runner; run the relevant checks locally before pushing.
- CLI builds need `JAVA_HOME` pointing at a JDK (there is no system `java` on PATH; Android Studio's JBR works, e.g. `JAVA_HOME=/opt/android-studio/jbr ./gradlew :app:testDebugUnitTest`) and the Android SDK location: `local.properties` (gitignored, `sdk.dir=...`) or `ANDROID_HOME`.
- Toolchain (see `gradle/wrapper/gradle-wrapper.properties`, `gradle/libs.versions.toml`, `app/build.gradle.kts`): Gradle 9.6.0, AGP 9.5.2, compileSdk 37.1 / targetSdk 37, minSdk 24, Java 11 bytecode. AGP 9 compiles Kotlin itself: do not add `org.jetbrains.kotlin.android`. The Gradle daemon uses Java 21 via `gradle/gradle-daemon-jvm.properties` and the foojay resolver. Some docs still quote API 35+; Gradle is authoritative.
- Module-level `repositories {}` blocks are rejected (`RepositoriesMode.FAIL_ON_PROJECT_REPOS` in `settings.gradle.kts`); add dependencies through the version catalog / `dependencyResolutionManagement`.
- Root `keystore.properties` is optional and gitignored. Release builds use it when present and remain unsigned otherwise. Never stage `keystore.properties`, `local.properties` or `*.logcat`; they may hold signing secrets or device data.
- No formatter/static-analysis setup beyond `lintDebug` (no ktlint/detekt/editorconfig); match the existing style.
- `bundle { language { enableSplit = false } }` in `app/build.gradle.kts` is load-bearing: the locale is switched at runtime (`LocaleHelper`), so an AAB with language splits could drop a bundled language. Don't remove it.

Unit tests are plain JUnit 4 (plus `kotlinx-coroutines-test` for suspend code); there is no Robolectric. `testOptions.unitTests.isReturnDefaultValues = true` makes Android stubs (e.g. `android.util.Log`) no-ops in JVM tests. Tests mirror main sources under `app/src/test/java/`. Extract parsing, filtering, permission-matrix and transition logic into pure functions rather than trying to unit-test Android/root code.

## Architecture and invariants

- `MainActivity` is the monitor-mode/compatibility entry point; `MonitorModeManager` performs the radio and `con_mode` changes.
- The locale is runtime-switched, so every Activity must override `attachBaseContext` with `LocaleHelper.init` + `applyLocale` (both `MainActivity` and `PixieDustActivity` do), and visible strings must resolve through that locale-wrapped context: `PixieDustViewModel` uses `LocaleHelper.applyLocale(application.applicationContext)` and `PixieDustRunner.create` receives the wrapped Activity context. Raw `applicationContext` keeps the system locale and silently ignores the toggle.
- The app is phone-only and portrait-locked by design: `supports-screens` excludes large screens, both activities set `screenOrientation="portrait"`, and `ChromeOsAbiSupport` is disabled in `app/build.gradle.kts`. It declares no `INTERNET` permission; don't add screens, orientations or network access as a drive-by fix.
- `DeviceCompatibilityChecker` performs real capture/injection and `con_mode` write tests. It disables WiFi before those tests, toggles the radio during capability checks and centralizes the final restore/restart; preserve that ordering to avoid extra WiFi drops. The check performs exactly one `con_mode` test write (inside `testCapabilities`), plus the restore of the original value in `finally`; do not reintroduce a separate write test, which added a second driver transition whose ~10 s sysfs write timeout killed the app through `ShellExecutor`'s reader threads (issue #5).
- A check persists a pending-restore marker (`PendingCompatRestore` in `CompatCheckRestore.kt`) before touching the radio and clears it in `checkCompatibility`'s `finally`. The marker uses synchronous commits, records a `radio_touched` flag before `svc wifi disable` (so a kill in that window still restarts WiFi), and stores the original `con_mode`. If the process dies mid-check, `MainActivity.onCreate` applies the pending restore on the next launch even when a cached result exists (it is skipped only while a check is in flight), verifying the framework state with retries and keeping the marker when the restore fails. `restoreIfPending` returns `true` only when the restore actually succeeded, so no success toast is shown for a failed restore. Both the check's write and the pending restore go through `writeConMode` (`echo $?` is parsed, because `su -c` reports the echo's exit code, not the redirection's), so a false `exitCode == 0` cannot clear the marker. Keep `isValidConModeRestoreTarget` validating the stored path/value before interpolating them into root commands.
- The check is never run automatically: only the "Verificar compatibilidad" button triggers it (it disrupts WiFi). Results are cached in `MainActivity` statics so `recreate()` does not rerun the disruptive test, and a recreated Activity waits for an in-flight check instead of starting a second one. Enabling monitor mode requires a prior verification in the process (otherwise a toast); disabling must always remain possible without one. `toggleEnabledForState` keeps that promise visually too: an unverified check leaves MANAGED locked while MONITOR (disable) and UNKNOWN (retry) stay actionable.
- `pendingRestoreInProgress` blocks both the verify button and the mode toggle while a pending restore is applied, so root commands cannot interleave and clear the marker mid-restore. On recreate, a rethrown `CancellationException` deliberately preserves the cached result while any other exception clears the cache and resets verification, so a failed check cannot leave monitor mode enabled.
- `resolveConModePath()` (top-level in `DeviceCompatibilityChecker.kt`) must retain root-based discovery: SELinux can hide `/sys/module` from the app UID, so a `File`-only scan misses valid paths.
- `MonitorModeManager`'s normal enable/disable writes are raw `echo 4/0 > $conModePath` via `execRoot` (with `CON_MODE_WRITE_TIMEOUT_MS`), not `writeConMode`'s `echo $?` parsing; don't assume the check's exit-code safeguard applies there.
- QCACLD monitors come up **detuned**: `con_mode=4`/`type monitor` leave the PHY on no frequency, so the radio receives 0 frames even next to many APs (the historical false "Captura no verificada"). `enableMonitorMode` and `testRealCapture` must `iw dev <iface> set channel N` — channel policy, rotation and validation are pure in `MonitorChannelPolicy.kt` (keep new decisions there with tests). Verify a tune by the `iw set channel` exit code, never by the `iw dev info` channel line: many drivers don't echo it in monitor, so tcpdump is the final judge (`isTuneAccepted`). `testRealCapture` must not run `svc wifi enable`: `ip link up` powers the radio with the framework off, and enabling it mid-test lets the system supplicant steal the interface. The persisted channel (`MonitorChannelStore`, default 6) drives both the enable-time tuning and the chip selector in `MainActivity` (`CHANNEL_CHIP_IDS`, visible only in MONITOR); DFS channels are deliberately excluded (no radar detection in the driver). There is deliberately **no auto-hopping mode**: external tools (airodump-ng, aireplay-ng) own the channel once monitor is up, and an app-side loop would race them; the chips only reflect the last channel AmWF applied, not necessarily the live one (see `docs/USER_GUIDE.md` §3.4).
- Use `ShellExecutor` for one-shot `su`/`sh` commands and keep its reader threads/timeouts; naive pipe reads can deadlock. Its reader threads must swallow `IOException`: killing a timed-out process closes the pipes from another thread, and an uncaught `InterruptedIOException` there crashes the whole app (issue #5). Con_mode writes use `CON_MODE_WRITE_TIMEOUT_MS` (30 s) because the driver reload can block ~10 s; the reader accumulators are synchronized because a descendant may keep the pipe open after `exec` returns. `SupplicantProcesses` and `PixiewpsExecutor` own long-lived processes that need streaming output.
- `PixieProcessSupport.pidWatchdogTail` must keep the watchdog as a single `sh -c` command: a multi-command background subshell makes Android's `sh` retain the stdout fd, so the reader does not see EOF until the timeout. `PixiewpsExecutor` also breaks on `PIXIEWPS_DONE_MARKER` as a fallback.
- With minSdk 24, API 26+ process calls (`destroyForcibly`, `Process.isAlive`, timed `waitFor`) must go through the `*Compat` helpers in `ProcessCompat.kt`.
- Watchdogs in `PixieProcessSupport` verify `/proc/<pid>/stat` starttime (field 22) before killing, so a reused PID cannot kill an unrelated root process; preserve this in any new watchdog.
- `diagnostics/` exports passive state plus the in-memory `AppLogger` through FileProvider. `DiagnosticsFormat` redacts MACs (to their OUI) and SSIDs, including SSIDs discovered from `iw dev`; preserve redaction for any new report field.
- In `wifi/pixiedust/`, `PixieDustRunner` orchestrates phases/retries and WiFi restoration. Its Android/process dependencies (supplicant, pixiewps, PSK extractor, native binaries, audit log, shell, WiFi state) are constructor-injected through the gateways in `PixieDustGateways.kt`; production wiring is `PixieDustRunner.create(context)`. Keep the runner free of `Context`: unit tests build it with fakes, so new dependencies must go through a gateway rather than inline `Context`/system-service access. `SupplicantProcesses`, `PixiewpsExecutor`, `PixiePskExtractor` and `PixieProcessSupport` own native-process work; `PixieAuditLog` persists audit logs.
- `cleanup()` must only `pkill` binaries whose cmdline starts with the app's bundled binary directory; never the system supplicant. It must confirm the framework WiFi state after `svc wifi enable` and retry: the command can return 0 without turning the radio on (seen on cancel). Confirmation is dual-source (`WifiRestore.combinedEnabled`: `dumpsys` grep with `-i`, matching `CompatCheckRestore.readWifiEnabledState`, plus `settings get global wifi_on`, which must agree) and must survive a settle re-read, because MIUI can report "enabled" for one instant and then revoke the toggle (field: cleanup left `wifi_on=0` and the Pixie scan then finds no radio). It is `@Synchronized` and `cleanupDone`-guarded because both `cancel()` and `finally` may call it.
- `runAttack` must persist the audit log on every exit path (validation, missing binaries, capture failure, success and cancellation) and flush the supplicant queue before cleanup, or the final M3 lines are lost. Logs in `/sdcard/AmWF/pixie-logs/` (fallback `filesDir/pixie-logs`) contain plaintext WPS/WPA credentials. The attack's `svc wifi disable` is covered by `PixieAttackRestore` (same pattern as `PendingCompatRestore`): `attackRestore.markWifiDisabled()` fires **before** the disable, `cleanup()` clears the marker only when the framework confirms the radio is back on (`restoreWifi()` returns the confirmed state), and both `MainActivity.onCreate` and `PixieDustActivity.onCreate` apply the pending restore — a process death mid-audit must never leave the user's WiFi off.
- After a successful M3 capture, close the WPS session (`wps_cancel`) before killing the attack supplicant. Otherwise the AP keeps its session open and the PSK extraction, which starts within seconds, collides with it (the AP retransmits M1 and the registrar fails with "Unexpected state"). `PixiePskExtractor` likewise cancels when provisioning ends without a PSK (field case: an AP that went silent after our M4 kept the session half-open and every retry collided) and best-effort on the user-cancellation path (`CancellationException`), so a Stop mid-extraction doesn't leave the session half-open either.
- `M3Parser` treats a `config_error=18` NACK after all 6 M3 fields as a complete capture, not a failure; exact M3 hex lengths (32/384/64 chars) are the guard against Android's truncated 32-byte dump.
- Hopeless APs abort early instead of burning rounds: association rejects go through the attack-wide `M3Parser.AssocRejectTracker` budget, silent M3 windows end as `M3Capture.NoResponse` with a localized reason — split by `M3Parser.bssidVisibleInSupplicantOutput` into "visible but WPS-stuck" (`pixie_reason_no_response_visible`) vs true out-of-range; the `wps_reg` command echo never counts as visibility — and `wps_reg` retries use progressive backoff. Cancels mid-capture log an honest interruption instead of a bogus failure.
- Pixiewps mode and budget are pure-function decisions in `PixieModeSelector`/`PixieDiagnosisParser`: force `--mode` only from captured M5/M7 (mode 3, RTL819x), never from the BSSID OUI — an OUI identifies the router vendor, not the chipset, so OUIs are log hints only. `PixiewpsPlan.timeoutSeconds` travels with the command so the watchdog and the deadline cannot diverge. Never add `--force`: it scans the whole epoch (~30 min on real hardware); when pixiewps suggests it, a `MIGHT_BE_VULNERABLE` diagnosis drives `RETRY_WITH_NEW_DATA` instead. Known limitation: the M5/M7 path passes only `-5`/`-7`, but pixiewps also requires `--r-nonce`, which AmWF does not capture.
- Pixie Dust UX is intentional: tapping an auditable network selects it and immediately starts the audit (the system WiFi is disabled before the attack when it is on and restored afterwards only if it was on); there is no Run button or confirmation dialog. Search, filters, session timer and collapsible console are intentional scope, not unused UI. The phase tracker (five-bar strip, formerly with "Preparar/Conectar/Handshake/Analizar/Clave" labels) was removed entirely: `PixieDustStage` carries only `progress`, there is no `PixieDustPhase`, and the stage title + percentage carry all the state — don't reintroduce a phase strip.
- Keep `MainActivity`'s Pixie Dust button enabled even when its alpha is dimmed. If compatibility already confirmed missing binaries, the tap shows the summary instead of opening the audit; otherwise it opens the screen.
- Route WiFi scan permission and location-services checks through `WifiScanPermissions`: precise location is required on every Android version, plus `NEARBY_WIFI_DEVICES` on Android 13+.
- `PixieDustViewModel.availableWifiInterfaces()` is non-root and best-effort by design: `NetworkInterface` needs the `INTERNET` permission the app deliberately doesn't declare (its enumeration always comes back empty — the `ifaddrs` EPERM in logcat is this), and ConnectivityManager only answers with a connected network, so "No se encontró interfaz WiFi disponible" on cold open is expected, not a bug. When detection finds nothing, `startAttack` resolves the real interface with root (`ls /sys/class/net`, parsed by the pure `interfacesFromSysfsListing`) before launching and flips `interfacesAvailable`, so `wlan0` is a fallback, never a guess. Keep that resolution at attack start, not screen open — the su prompt belongs where root work is expected.
- `PixieDustReducers.kt` holds the ViewModel's UI-state decisions as pure functions (`attackStartError`, `canStartScan`, `sortNetworksForList`, `attackOutcomeStage`, `*State` transitions); `PixieNetworkFilter.kt` does the same for the network picker (search, chips with live counts via `networksMatchingFilter`, dual-band, plus strong-signal — field-derived −70 dBm threshold — and WPS-locked filters). New UI-state decisions go there with unit tests, not inline in the ViewModel/Activity.
- Validate BSSID/interface input and shell-quote user-controlled values before privileged commands.

## Native Pixie Dust binaries

`app/src/main/assets/wifi/` contains prebuilt ARM binaries (ABI filters: arm64-v8a, armeabi-v7a); normal Gradle builds do not compile them.

- Rebuild with `./scripts/build-wifi-binaries.sh <arm64-v8a|armeabi-v7a>`. Requires NDK r27+ (`ANDROID_NDK`/`ANDROID_NDK_HOME`) and sibling trees `../pixiewps-master`, `../wpa_supplicant-2.11`, `../libnl-3.2.25`. The script applies the patches in `scripts/patches/` (libnl against wpa_supplicant 2.11, supplicant stdout flush).
- The arm64-v8a ELF `LOAD` segments must be **16 KB-aligned** (`-Wl,-z,max-page-size=16384`, enforced and verified by the build script): Android 15+ on 16 KB-page devices won't load 4 KB-aligned binaries, and Play has rejected targetSdk 35+ updates without it since 2025-11-01. `armeabi-v7a` is exempt. Android Studio's "not compatible with 16 KB devices" APK warning must be clean before any Play upload.
- arm64-v8a builds `pixiewps`, `wpa_supplicant`, `wpa_cli` and libnl. armeabi-v7a builds only `pixiewps_32`; `wpa_supplicant_32` is intentionally absent and `wpa_cli_32` is a preserved prebuilt asset.
- `NativeBinaries` is the single source of truth for paths, missing-binary detection and messages: `missingBinariesMessage` for detailed failure reasons, `missingBinariesSummary` for compatibility/warning UI. Keep all callers using it.
- Call `NativeBinaries.ensure(context)` before `missingCriticalBinaries()`. Assets are copied lazily on first launch and after app updates, so checking first falsely reports missing binaries.
- Never substitute Android's system `wpa_supplicant`: `CONFIG_ANDROID_LOG` truncates WPS hexdumps to 32 bytes. The bundled supplicant is mandatory for complete M3 capture.
- `wpa_cli` and `pixiewps` fall back to system paths (`/system/bin`, `/vendor/bin`, `/vendor/bin/hw`, `/system/xbin`, `/odm/bin`) when the bundled asset is missing; the "Binarios Pixie Dust" row can show available because of that. `wpa_supplicant` never falls back.
- Supplicant control dir comes from `NativeBinaries.ctrlDir()`: `/data/vendor/wifi/amwf` on API 28+, `/data/misc/wifi/amwf` below; devices upgraded to P (not launched with it) keep the legacy path, so if the supplicant fails with "socket not created", try the other directory.
- The runtime supplicant config must be staged into `ctrlDir` via `su` stdin (`execRootWithInput`): the `su` SELinux domain cannot read `filesDir`. Keep `update_config=1` so `save_config` can persist the PSK after WPS provisioning. It also stages a global `freq_list=<target freq>` (validated against the bundled 2.11 binary: accepted as a global param and applied by scan.c's "Optimize scan based on conf->freq_list" path), restricting every `wps_reg` scan to the target channel — without it each attempt sweeps the whole 2.4+5 GHz band (~2-4 s) and floods the audit log with third-party SSIDs. An unknown or out-of-range freq omits the line (full-band fallback); keep that graceful path in `buildRuntimeConfigContent`. If a restricted round never sees the target BSSID, the attack spends its single full-band retry round (`shouldFallbackToFullBandScan`) before declaring out-of-range — covers an AP that changed channel after the UI scan.
- `BINARIES_SETUP.md` documents the native rebuild workflow, SELinux notes and the system-binary fallback (in English); `THIRD-PARTY-NOTICES.md` lists bundled binaries, their versions and licenses; `SECURITY.md` tells reporters how to disclose safely. Trust them over older notes.

## Conventions

- Spanish is the default UI language (`res/values/strings.xml`); English is `res/values-en/strings.xml`. Add every user-facing string to both.
- Comments and log messages are predominantly Spanish; match the surrounding file.
- New main-source Kotlin files need the `SPDX-License-Identifier: GPL-3.0-or-later` header.
- Use `ShellExecutor.logD/W/E` for diagnostics-relevant logging so it reaches `AppLogger`. Exception: `PixieDustRunner.log` intentionally uses raw `Log.d` because its lines contain M3 material and PIN/PSK; `AppLogger` is exported in diagnostics, so never route audit output through it.
- Commits follow Conventional Commits (`feat|fix|refactor|docs|chore|build(scope): summary`, English subject). Release commits bump `versionCode` and `versionName` in `app/build.gradle.kts` and use `chore(release): ...`.
- Store metadata lives under `fastlane/metadata/android/<locale>/` (en-US, es-ES); changelogs are named `<versionCode>.txt` (currently `6.txt`, matching `versionCode = 6`). Play Console uploads are manual — there is no publishing automation in the repo.
